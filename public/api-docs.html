SysRepWeb — API de Integração

API REST para integração com sistemas ERP externos. Expõe pedidos, clientes, produtos e formas de pagamento gerados pelo sistema de força de vendas.

REST JSON Bearer Token

Visão Geral

Todos os endpoints retornam dados em formato JSON com codificação UTF-8. As requisições devem ser feitas via HTTPS.

Base URL
https://api.nresolutions.com.br/api/v1

id_parceiro — Controle de duplicidade

Disponível em clientes e produtos. Use para armazenar o ID do registro no seu ERP. Garante que em caso de timeout no POST você possa reenviar a requisição com segurança — se o registro já existir, a API retorna 409 Conflict com o id do registro existente, sem criar duplicata.

Paginação

Endpoints de listagem suportam paginação via parâmetros page e limit. O padrão é 100 registros por página.

ParâmetroPadrãoMáximo
page1—
limit100500

A resposta inclui o objeto meta com informações de paginação:

Exemplo de meta paginação
"meta": {
  "total": 348,
  "page": 1,
  "limit": 100,
  "pages": 4
}

Autenticação

A autenticação é feita via API Key, enviada no header de todas as requisições.

Header obrigatório:
Authorization: Bearer SUA_API_KEY
⚠️ Nunca exponha sua API Key em código front-end ou repositórios públicos. Em caso de comprometimento, solicite a revogação imediata.
Rate limit: 600 requisições por minuto por API Key. Ao atingir o limite a API retorna 429 Too Many Requests com o header RateLimit-Reset indicando quando o limite é liberado.
Exemplo de requisição 
curl -X GET "https://api.nresolutions.com.br/api/v1/pedidos" \
  -H "Authorization: Bearer SUA_API_KEY" \
  -H "Content-Type: application/json"

Para obter sua API Key, entre em contato com o suporte da NC Sistemas.

PATCH /pedidos/:id Atualiza status do pedido ▼

Permite que o ERP atualize o status de um pedido. Dois status são aceitos:

  • FATURADO — ERP recebeu o pedido e emitiu a nota fiscal
  • CANCELADO — ERP ou vendedor solicita cancelamento do pedido
⚠️ Somente sistemas autenticados com API Key podem alterar o status. O vendedor não tem acesso a este endpoint.
Body (JSON)
CampoTipoObrig.Descrição
statusstringSimFATURADO ou CANCELADO
id_parceirostringOpcionalID do pedido no sistema do ERP (para rastreabilidade)
observacaostringOpcionalObservação sobre a atualização
Exemplo — marcar como FATURADO
PATCH /api/v1/pedidos/1042
Content-Type: application/json
Authorization: Bearer SUA_API_KEY

{
  "status": "FATURADO",
  "id_parceiro": "NF-000123"
}
Resposta — 200 OK
{
  "data": {
    "id": 1042,
    "status": "FATURADO",
    "atualizado_em": "2026-06-03T10:00:00.000Z"
  }
}

Códigos de Resposta

A API utiliza os códigos HTTP padrão para indicar sucesso ou falha nas requisições.

CódigoStatusDescrição
200 OK Requisição bem-sucedida
400 Bad Request Parâmetros inválidos ou ausentes
401 Unauthorized API Key ausente, inválida ou revogada
404 Not Found Recurso não encontrado
409 Conflict Registro já existe — id_parceiro duplicado
429 Too Many Requests Limite de 600 req/min por API Key atingido
500 Internal Server Error Erro interno — contate o suporte
Exemplo de resposta de erro
{
  "error": {
    "code": 401,
    "message": "API Key inválida ou não autorizada"
  }
}

FAQ — Integração ERP

Dúvidas frequentes de desenvolvedores ao integrar o ERP com a API SysRepWeb.

Como fazer sincronização incremental sem trazer a base inteira? ▼

Use o parâmetro atualizado_apos disponível em GET /clientes e GET /produtos.

Estratégia recomendada
// 1ª sync: base completa — grave o timestamp de início
GET /api/v1/produtos?limit=500&page=1
GET /api/v1/produtos?limit=500&page=2
// salvar: lastSync = "2026-06-10 08:00:00"

// Syncs seguintes: somente o delta
GET /api/v1/produtos?atualizado_apos=2026-06-10%2008:00:00
GET /api/v1/clientes?atualizado_apos=2026-06-10%2008:00:00
A resposta inclui o campo updated_at em cada registro para você confirmar a data de atualização.
POST /clientes aceita número, bairro e complemento no mesmo request? ▼

Sim. Os campos numero, bairro e complemento são aceitos diretamente no POST /clientes. Não é necessário fazer POST + PATCH para completar o endereço.

Exemplo — endereço completo em um único POST
POST /api/v1/clientes
{
  "nome": "Farmácia São João",
  "cnpj": "12.345.678/0001-90",
  "endereco": "Rua das Flores",
  "numero": "100",
  "complemento": "Sala 2",
  "bairro": "Centro",
  "cidade": "Bauru",
  "uf": "SP",
  "cep": "17000-000",
  "id_parceiro": "CLI-ERP-0058"
}
O campo codigo do produto é o mesmo que aparece nos itens do pedido? ▼

Sim. O codigo informado no POST /produtos é armazenado como referência e retorna como itens[].codigo em GET /pedidos e GET /pedidos/:id. Use o código interno do seu ERP neste campo para casar os itens do pedido com seu catálogo.

Fluxo recomendado: ao sincronizar o catálogo (POST /produtos), envie codigo=SEU_COD_ERP e id_parceiro=SEU_ID_UNICO. Ao receber pedidos, case por itens[].codigo.
Preciso enviar preco_atacado e preco_promocao se meu ERP só tem um preço? ▼

Não. Ambos os campos são totalmente opcionais. Se não enviados, ficam como 0 e o vendedor terá apenas o preco_venda disponível ao montar o pedido. Nenhuma regra de negócio exige que estejam preenchidos.

Minha API Key já filtra por fornecedor automaticamente? ▼

Não. A API Key autentica e dá acesso ao banco de dados do seu tenant (empresa), mas não filtra por fornecedor automaticamente. O conceito de "fornecedor" dentro do SysRepWeb representa as indústrias/distribuidoras cujos produtos os vendedores comercializam.

Ao criar produtos, informe cod_fornecedor para associar ao fornecedor correto. Para listar produtos de um fornecedor específico, use o parâmetro id_fornecedor no GET /produtos. Para obter os IDs dos fornecedores cadastrados, consulte o administrador do sistema.

Como representar formas de pagamento com múltiplas parcelas (ex: 30/60/90)? ▼

A API não possui estrutura de parcelas múltiplas. A convenção é criar uma única forma de pagamento com a combinação de prazos na descrição. O campo prazo_padrao representa o prazo da primeira parcela.

Exemplo — boleto parcelado
POST /api/v1/formas-pagamento
{
  "descricao": "BOLETO 30/60/90",
  "prazo_padrao": 30
}

O vendedor vê a descrição completa ao selecionar a forma de pagamento no pedido.

Como casar o cliente de um pedido com o cadastro do meu ERP? ▼

Recomendamos manter um mapeamento local id_sysrep → id_erp. Duas estratégias:

  • Clientes criados via API: ao fazer POST /clientes com id_parceiro=SEU_ID_ERP, grave o id retornado no banco local. Use esse mapeamento para resolver pedido.cliente.id.
  • Clientes pré-existentes: faça GET /clientes uma única vez, a resposta inclui id_parceiro e cnpj — case pelo CNPJ ou id_parceiro e construa o de-para.
💡 O campo id_parceiro é retornado no GET /clientes — use-o como chave de integração primária.
Após marcar um pedido como FATURADO ou CANCELADO, o vendedor é notificado? ▼

Sim. A alteração de status é imediata e visível no app do vendedor na próxima atualização da lista de pedidos.

  • FATURADO: o pedido aparece como faturado — o vendedor sabe que o ERP recebeu e emitiu a NF.
  • CANCELADO: o pedido aparece como cancelado e fica bloqueado para edição no app.
⚠️ A operação é irreversível via API. Para reabrir um pedido cancelado é necessário acesso ao painel administrativo.
Qual o limite de requisições por minuto? ▼

O limite é de 600 requisições por minuto por API Key. Ao atingir o limite, a API retorna 429 Too Many Requests. O header RateLimit-Reset indica o timestamp (Unix) em que o limite é liberado.

Para sincronizações em lote com 1.500 produtos e limit=500, serão 3 requisições — muito abaixo do limite.
